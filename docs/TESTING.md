# 測試說明

## 自動化測試（雲函數）

```bash
npm run cloud:test
```

測試不需要微信環境：`cloudfunctions/game/test/fakeDb.ts` 是一個記憶體版雲資料庫，
實作了本專案用到的全部操作（`doc().get/update/set/remove`、`add`、`where().get/count/update/remove`、
`orderBy/limit`、`_.inc/max/push/pull/neq/lt/in/nin`），**每個操作本身原子、操作之間有隨機延遲**，
所以 `Promise.all` 的併發測試會真正交錯執行。

### 覆蓋範圍（46 個案例）

| 類別 | 案例 |
| --- | --- |
| 建立 / 加入 | 房間碼格式、撞碼重試、加入順序、不存在的房間、重複加入回到原位、**12 人上限 + 三人併發搶最後一席只成功一人**、開始後不能加入但原成員可重回 |
| 準備 / 開始 | 非房主、人數不足、有人未準備、**重複按開始只建一個回合**、開始後不能改準備狀態 |
| 離開 / 移除 | 房主轉移、最後一人離開自動關閉、只有房主能移除、被移除後可重新加入 |
| 出題 | 只有出題者能出、出題前不能投票、出題後不能改 |
| 匿名投票 | 每人一票、重複投票拒絕且不影響計數、非成員 / 錯誤 roundId / 非布林值拒絕、**6 人同時投票（重複 5 次）只發生一次階段轉換**、同一人連點只算一票 |
| 猜測與驗證 | 全對 `true`、一題錯 `false`、**回應只含布林值**、名單缺人 / 多人 / 含自己 / 非布林都拒絕、**併發重複提交回傳相同結果且只存一筆（不可暴力破解）**、投票未結束不能猜、`syncState` 只回本人結果且公開資料無 answer 欄位 |
| 結算 / 回合切換 | 全員確認後換下一位出題、私有狀態重置、**出題順序循環**、併發與重複確認只開一個新回合、房主強制下一回合、結束遊戲後所有操作拒絕 |
| 斷線 / 重連 | `syncState` 還原 hasVoted 與階段、`setPresence` 離線標記、**投票中有人離開自動推進**、投過票的人離開會重算、**猜測中有人離開舊名單被拒**、**出題者離開由下一位接手**、結算中有人離開、剩不到 2 人自動結束、離開後舊 roomId 不可用 |
| 非法操作 | 偽造 roomId、非成員讀寫、未知 action、非物件 payload、缺少 openid、pid 不可逆、公開集合不含答案欄位、錯誤階段操作 |

### 新增測試

`test/helpers.ts` 提供：

- `createTable(n, { start })`：建立 n 人房間（可直接開局）
- `ask(t)` / `voteAll(t, answers)` / `perfectGuess(t, me, answers)`
- `room(t)` / `round(t)`：直接讀取資料庫中的房間與回合
- `expectGameError(promise, code)`

## 前端型別檢查與建置

```bash
npm run typecheck      # tsc --noEmit
npm run build:weapp    # Taro 建置，應顯示 Compiled successfully
```

前端沒有單元測試：三個頁面的邏輯幾乎都是「呼叫雲函數 → 顯示結果」，
行為正確性主要由雲函數測試保證，UI 以下列手動腳本驗證。

## 手動測試腳本（開發者工具多賬號 或 真機）

準備 3 個以上帳號 A（房主）、B、C。

1. **建房與加入**：A 建房；B、C 輸入房間碼加入。三個畫面都應即時看到三位玩家。輸入錯誤房間碼應提示「找不到這個房間」。
2. **準備與開始**：A 的開始按鈕應顯示「等 2 人準備」；B、C 準備後變為「開始遊戲」。B 嘗試在未準備時 A 按開始 → 錯誤提示。
3. **出題**：A 看到輸入框與靈感；B、C 看到「A 正在出題」。A 公布後三人同時進入投票畫面。
4. **投票**：各自投票；投票後顯示「已收到你的答案 n/3」。確認 B 的畫面看不到 A 投了什麼。全部投完自動進入猜測。
5. **猜測**：每人只看到其他兩人；未選完時按鈕顯示「還有 n 個人沒猜」。送出後顯示進度。
6. **結算**：故意讓 A 全對、B 錯一題。A 看到「恭喜！你全部猜對了！」、B 看到「很可惜」。B 的畫面上不能有任何線索顯示錯了幾題或誰的答案。
7. **下一回合**：三人按「看完了」→ 第 2 回合，由 B 出題。A 在結算頁應看到「房主：不等了」按鈕。
8. **重連**：投票階段把 C 的小程序關掉（真機：上滑關閉；工具：關閉視窗）→ 重開 → 首頁顯示「回到房間」→ 回到投票頁，若 C 已投過應顯示等待而非再投一次。
9. **離線卡關**：C 關掉後不回來；A 打開右上角玩家面板 → 移除 C → 若 A、B 都已投票應立即進入猜測。
10. **分享（真機）**：大廳按「用微信邀請朋友」→ 好友點開卡片 → 首頁房間碼已自動填入。
11. **結束**：A 結束遊戲 → 所有人看到結束畫面與總回合數。

## 尚未驗證的項目

以下只能在真實微信環境確認，本專案開發環境無法執行：

- 雲資料庫 `watch` 的實際延遲與重連行為
- `_.nin` 用在陣列欄位的查詢語意（MongoDB 標準行為，微信文件亦如此描述，但未實測）
- `where({ _id }).update()` 條件式更新在雲端的行為
- 微信分享卡片、`type="nickname"` 暱稱快填、`vibrateShort`
- 雲函數冷啟動時間（預估 1–2 秒）
